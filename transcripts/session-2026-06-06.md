**Assistant:** *(Read admin.py, found the bug)*

Found the core bug. Here's what's happening:

`usage.date` is a plain `DATE` column (not a timestamp). `_LOCAL_DATE` does `DATE(date::timestamptz AT TIME ZONE tz)`. When PostgreSQL casts a plain `DATE` to `timestamptz` it assumes **UTC midnight**, so `2026-06-06` becomes `2026-06-06 00:00:00+00`. Then converting to Pacific gives `2026-06-05 17:00` — which is **June 5th**. So every UTC-day row shows up as the previous day in the admin view, and `uploads_today` is always 0.

Fix: since `usage.date` is already a plain date stored in UTC, **don't convert it** — just use the column directly. And make the rate limit also explicitly use UTC.

**User:** Quick question, what is client-side vs server-side, I though the backend is the server and the client-side is the interface. is redact in server or client?

**Assistant:** You're right on the definitions:

- **Client-side** = runs in the user's browser (React, JavaScript, canvas)
- **Server-side** = runs on your backend (FastAPI, Python)

The redaction flow is actually **split**:
- **Drawing the boxes** → client-side (React canvas in the browser)
- **Rendering PDF pages for preview** → `/redact/preview` → server-side (PyMuPDF on the backend)
- **Actually burning the black boxes into the PDF** → `/redact/apply` → server-side (PyMuPDF on the backend)

So the TA's description of "client-side" is slightly inaccurate. The PDF does get sent to your server for both preview and apply. What's true is that **no AI is involved** — it's just PDF rendering/manipulation on your backend, not Claude. The blacked-out content isn't sent to the LLM.

So the more accurate thing to say in the UI and the REVIEW-PLAN is: "no AI is involved in this step" rather than "happens in your browser." Want me to correct the wording in both places?

**User:** Is there a way to keep this whole thing in the client-side or should I just say that I want to keep the logic separate where server handles all the business logic while the client-side is purely for interface with the preview and then displaying information

**Assistant:** The second option is the right architectural call. You *could* do pure client-side PDF manipulation using a library like `pdf-lib` or `pdfjs`, but:

- PyMuPDF on the backend does a much more thorough job (properly burns the pixels, strips underlying text layer too so the redacted content can't be copy-pasted out)

The "server handles business logic, client handles interface" separation is actually the correct and professional approach. It's called a **thin client** architecture and it's standard for web apps.

The TA's feedback was really just about transparency in the UI — not about where the code runs. So the honest and accurate thing to say is: **"no AI processes your PDF during redaction — it's handled by our server using a PDF library, and the content you black out is never sent to the AI."**
